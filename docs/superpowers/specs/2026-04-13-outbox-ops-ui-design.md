# Outbox 运维模块 UI 优化设计

**日期**: 2026-04-13

## 目标

优化 `/admin/outbox-ops` 的信息架构和视觉层级，使其在设计语言上贴近系统设置模块，同时强化运维场景的状态识别与排障效率。

本次设计要达成三个结果：

- 页面从“基础双栏工具页”升级为“混合式运维控制台”
- 保留现有核心工作流：筛选事件 -> 查看详情 -> Dry Run -> Replay
- 在不扩后端接口的前提下，补足全局健康感知、当前筛选摘要、右侧工作台语义和结果反馈

## 本批范围

仅处理前端 Outbox 运维页面及其直接相关组件：

- `src/views/OutboxOps.vue`
- `src/components/outbox/OutboxEventTable.vue`
- `src/components/outbox/OutboxReplayPanel.vue`
- 可能新增少量 Outbox 专用展示组件或局部计算逻辑
- `src/views/__tests__/OutboxOps.behavior.test.js`
- 必要的本地化文案

## 现状

当前页面已经接入 `ManagementListShell`，但整体仍是最小可用形态：

- 顶部只有标题、副标题、三个筛选项和一个刷新按钮
- 主区域是左侧事件表格 + 右侧 replay 卡片
- 缺少页面级摘要，无法快速判断当前系统是否积压或故障
- 右侧工作台虽然能执行操作，但上下文不足，更多像“孤立按钮面板”
- 页面与系统设置模块相比，缺少更强的分区感、过渡感和运维语义

## 用户确认结论

与用户确认后的设计方向如下：

- 结构采用“混合式”
  先展示概览与状态摘要，再保留下方双栏事件工作区
- 概览层同时包含：
  - 全局健康概览
  - 当前筛选结果摘要
- 视觉语气采用“系统设置页基础上增加运维警戒感”
  保持统一设计语言，但对失败、待处理、Replay 结果做更明确的状态提示
- 视觉方案采用“方案 2 · 信号驱动控制台”
  平衡系统设置的一致性和运维台的状态识别

## 方案比较

### 方案 A: 仅做视觉对齐

优点:
- 改动面小
- 风险低
- 能快速拉近与系统设置页的一致性

缺点:
- 不能解决运维页面“缺摘要、缺路径、缺状态信号”的核心问题
- 用户在筛选和重放时仍需要自己拼装上下文

### 方案 B: 混合式运维控制台

优点:
- 保留现有高效双栏工作流
- 通过双层摘要补足“全局健康 + 当前聚焦”两类认知层
- 与系统设置页保持统一，同时为失败和回放结果增加足够的运维信号
- 不依赖新增接口，落地成本可控

缺点:
- 需要在前端增加事件汇总与衍生状态逻辑
- 组件拆分会比纯视觉调整多一步

### 方案 C: 专用高密度运维台

优点:
- 状态扫读效率最高
- 运维语义最强

缺点:
- 与系统设置页视觉差异过大
- 视觉压力偏高，不适合后台常驻管理场景
- 超出本次“参考系统设置模块”的主方向

## 采用方案

采用方案 B。

原因：

- 它直接回应了用户选择的“混合式 + 双层摘要 + 方案 2 + 设置页基础上增加运维警戒感”
- 它保持了 Outbox 运维当前最有效的排障路径，不强行改造成多标签或深层切换结构
- 它能在现有数据接口约束内完成明显升级，不把需求扩展成后端统计项目

## 设计

### 1. 页面骨架

页面采用三层结构：

1. 顶部页头区
2. 中部摘要区
3. 底部双栏工作区

页头区继续沿用设计系统的页头表达，但增加一条运维提示带，明确：

- 本页用于排查副作用链路
- Dry Run 是推荐默认路径
- Replay 不改主业务事实，只重放 side effect

这样用户进入页面时先理解边界，再进行操作。

### 2. 摘要区

摘要区拆成两层，语义不同，视觉权重也不同。

#### 2.1 全局健康概览

第一排用于表达系统层面的 Outbox 健康状态，不受当前筛选影响。

该排卡片基于当前加载到的事件集合做前端汇总，至少包含：

- 总事件数
- 失败消费者数
- 待处理 / 处理中消费者数
- 最近事件时间

这里的“全局”是页面当前拿到的数据全集，而不是新增后端统计接口意义上的全库全局。
如果后续需要真正的系统级健康看板，应独立追加后端统计接口，不包含在本次设计中。

#### 2.2 当前筛选结果摘要

第二排用于表达用户当前筛选上下文下的结果状态，强调“你现在看到的范围”。

建议包含：

- 当前命中事件数
- 当前范围内失败 job 数
- 当前范围内需要关注的状态标签
- 当前筛选条件摘要或空筛选提示

该层摘要应比全局概览更贴近实际操作，并在用户修改筛选后即时刷新。

### 3. 双栏工作区

双栏工作区继续保留，以保证排障效率。

#### 3.1 左栏：事件队列台

左栏承担“查找和选择事件”的任务，内部结构调整为：

- 顶部工具栏
  - 事件类型
  - 消费者名称
  - 消费状态
  - 刷新按钮
- 工具栏下方的结果上下文
  - 当前命中数
  - 是否存在失败项
  - 当前是否处于空筛选状态
- 事件表格

表格增强点：

- 行点击后具有稳定选中态
- `consumerJobs` 使用更易扫读的 badge 分组
- 失败或待处理状态在行内可快速识别
- 时间列保持较弱视觉权重，避免和事件类型抢主次

#### 3.2 右栏：Replay 工作台

右栏不再是单张单义卡片，而是一个连续的操作面板，内部至少拆成三个区块：

- 选中事件摘要
  - 事件类型
  - 事件 ID
  - 聚合 ID
  - 消费者执行概况
- Replay 操作区
  - 目标 consumer 输入
  - Dry Run 按钮
  - Execute Replay 按钮
  - 风险提示或管理员限制提示
- 最近结果区
  - 最近一次 Dry Run / Execute 的返回结果
  - 结果采用更像“工作台输出”的深色代码块或日志区承接

空状态下，右栏不只是提示“先选择事件”，还要解释选中后能做什么。

### 4. 视觉与状态语气

整体视觉基调沿用系统设置页：

- 浅色背景
- 统一圆角半径
- 卡片式分区
- 中性主色和克制阴影

在此基础上，增加有限但明确的运维信号：

- 普通信息保持中性
- `pending` / `processing` 使用轻度信息色
- `failed` 使用更清晰的警示色
- Replay 执行结果根据成功 / 失败 / dry-run 做不同重点表达

原则是“关键位置发声，非关键位置克制”，避免整页变成报警墙。

### 5. 组件拆分建议

优先复用现有设计系统组件：

- `ManagementListShell`
- `PageHeader`
- `StatePanel`
- `MetricTile`

推荐补充的 Outbox 页面内聚组件：

- `OutboxOpsSummaryMetrics`
  用于渲染两层摘要卡片
- `OutboxOpsBanner`
  用于承接页头下方的运维提示带
- `OutboxSelectionSummary`
  用于右栏顶部的选中事件摘要

如果组件数量控制得当，也可以先不单独拆文件，在 `OutboxOps.vue` 内组织，但逻辑应保持分段清晰。

### 6. 数据与状态边界

本次不新增后端接口，数据能力保持为：

- 事件列表
- 单条事件详情
- Replay 执行结果

因此需要在前端做以下衍生计算：

- 从 `events` 汇总摘要指标
- 从 `consumerJobs` 归纳失败数、待处理数和最近关注项
- 维护当前选中事件及其高亮状态
- 在刷新事件列表时合理处理右侧详情与最近结果的保留/清理策略

建议保持以下行为：

- 刷新列表时清空最近 replay 结果
- 重新选择事件时清空 consumer 定向输入
- 当筛选后当前选中事件不在结果集中时，右栏回到空状态或重新拉取首个有效项

### 7. 交互节奏

页面应引导一个明确操作顺序：

1. 看页头提示和摘要，判断是否存在异常
2. 用筛选缩小范围
3. 在左栏选择具体事件
4. 在右栏先看上下文
5. 先执行 Dry Run
6. 再决定是否 Execute Replay
7. 在结果区查看执行反馈

其中：

- `Dry Run` 是推荐默认动作，应弱化误触 `Execute Replay` 的风险
- `Execute Replay` 是主操作，但需要更强的谨慎语义
- 结果区要让用户明显知道这是“最近一次操作结果”，而不是系统实时状态

### 8. 文案与本地化

需要为以下内容补充或调整文案：

- 页头提示带
- 两层摘要卡片标题和辅助文案
- 左栏结果上下文提示
- 右栏空状态与风险提示
- Replay 结果标题

文案风格应延续当前中文后台语气：

- 简洁
- 明确
- 避免技术营销式措辞

### 9. 测试策略

至少覆盖以下层级：

- `OutboxOps.behavior.test.js`
  - 页面仍渲染事件区和工作台
  - 新摘要区存在
  - 运维提示区存在
- 如果引入摘要计算 helper：
  - 增加纯函数测试，锁定失败数、待处理数、最近时间等汇总逻辑
- 如果表格或右栏新增关键状态表达：
  - 用组件测试锁定关键文案和空状态

本次不要求视觉快照测试，但需要保证行为测试覆盖新的主要结构。

## 不处理内容

本批不处理：

- 新增后端全局统计接口
- Outbox 事件分页、排序、批量选择
- 多步确认弹窗或审批流
- 审计日志页联动跳转
- 重写现有 Replay 后端权限模型

## 风险与控制

- 风险: “全局健康概览”被误解为系统级真实全局统计
  控制: 文案明确为当前已加载事件视图的健康概览，避免伪全局表达

- 风险: 前端摘要计算和后端实际语义不一致
  控制: 汇总逻辑只基于现有 `events` / `consumerJobs` 字段，不做额外业务推断

- 风险: 视觉增强后页面显得过重，偏离系统设置模块
  控制: 只在失败、待处理、执行结果等关键位置提高状态色权重

- 风险: 刷新和重放后的右侧状态容易残留旧上下文
  控制: 明确列表刷新、事件切换、详情刷新时的清理与保留策略，并通过测试锁定

## 实施顺序

建议按以下顺序实现：

1. 先补行为测试和必要的摘要计算测试
2. 重构 `OutboxOps.vue` 页面骨架，加入页头提示与双层摘要
3. 增强 `OutboxEventTable.vue` 的行内结构和选中态
4. 增强 `OutboxReplayPanel.vue` 的事件摘要、操作分区和结果区
5. 补齐本地化文案
6. 跑测试并调整细节
