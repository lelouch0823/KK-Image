# AI 模块整体优化设计

**日期：** 2026-03-09

## 目标

在不改变现有 AI 对外接口与核心业务能力的前提下，对前后端 AI 模块进行一次“分层收敛型”优化，解决以下问题：

1. 前端聊天组件职责过重，后续迭代成本持续上升。
2. 流式文本、动作卡片、消息持久化存在重复状态源，容易产生错位与覆盖。
3. 后端 AI 路由文件承担过多职责，普通问答、流式输出、动作编排、报告生成和遥测混杂在同一入口。
4. 补槽、预览、确认、提交流程虽然已具备雏形，但交互恢复能力和结构稳定性仍不足。
5. 错误分类、失败恢复与可观测性较为分散，问题排查成本高。

这次优化的目标不是重写 AI 模块，而是在控制改动范围的前提下，让结构更清晰、交互更顺滑、状态更稳定、后续扩展更可控。

## 问题概述

### 1. 前端职责堆叠

当前 `src/components/common/AIChatWidget.vue` 同时负责：

1. 弹窗布局、拖拽与缩放
2. 消息列表和历史持久化
3. 图片上传、拖放、粘贴与压缩
4. 建议词、报告生成
5. AI 请求发送与流式接收
6. `slot_request` / `action_preview` / `action_result` 渲染与交互

这会导致任何一个 AI 交互细节调整，都容易牵连窗口层、消息层和动作层逻辑。

### 2. 状态源重复

当前至少存在三类状态并行维护：

1. 文本流状态
2. assistant 消息状态
3. actionCard 动作状态

`src/composables/useAIStream.js` 已经维护了 `displayedContent`、`fullContent`、`toolStatus`、`actionCard`，而 `src/components/common/AIChatWidget.vue` 仍在 watcher 中重复拼接消息、渲染 markdown、修复最终内容并落盘。双状态源容易引发以下问题：

1. 最后一条 assistant 消息被覆盖或状态滞后
2. action card 与文本消息生命周期不一致
3. 流结束时的最终落盘逻辑依赖隐式时序

### 3. 后端路由职责过重

当前 `functions/lib/hono/routes/manage/ai.js` 同时承担：

1. 运行时 AI 配置加载
2. prompt injection 检测与日志记录
3. 普通问答 chat
4. SSE 流式对话 stream
5. AI 报告生成 report
6. action orchestration 接入
7. SSE 解析与 gate 过滤
8. tool round 调度
9. 模型切换遥测

这会导致：

1. chat / stream 行为容易分叉
2. 新增能力时只能继续堆到大文件中
3. 单点修改的回归影响面过大

### 4. Action 流程可维护性不足

当前 `functions/ai/action-orchestrator.js` 已经形成了较好的创建流程雏形，但还有两个明显问题：

1. 候选项选择逻辑更偏向“单槽位、单轮补全”的 happy path，多字段并发待补场景扩展性不足。
2. 前端补槽卡片 `src/components/common/ai/SlotQuestionCard.vue` 选中后直接锁定字段，误选后的恢复路径不够清晰。

### 5. 错误恢复与可观测性分散

目前前端能区分部分图片能力错误，后端也记录了部分 injection / model / gate telemetry，但整体仍缺少统一抽象：

1. 用户看到的是零散 toast，不一定知道当前流程卡在何处。
2. 服务端日志字段较分散，排障需要跨多段逻辑拼凑信息。
3. tool 调用轮次上限等关键失败，在用户侧反馈不够明确。

## 选定方向

采用**分层收敛型优化**，而不是小修小补或全面重写。

核心原则：

1. 尽量保持现有 API 协议和业务语义稳定。
2. 优先收敛结构、状态和交互，而不是扩大功能面。
3. 把“文本问答”和“业务动作”分成清晰的两条主线。
4. 把隐式时序副作用改成显式状态流。
5. 通过测试锁定关键行为边界，降低后续迭代回归风险。

这个方向兼顾了收益与风险：既能明显改善当前 AI 模块的可维护性，又避免一次性进行高风险的平台化重构。

## 范围

### 纳入范围

1. 前端 AI 聊天组件拆层与状态收敛
2. 流式文本、动作卡片与消息落盘生命周期统一
3. 后端 AI 大路由按职责拆分为更薄的协作层
4. 补槽、预览、确认、提交的交互体验优化
5. 统一错误分类、失败恢复策略与关键遥测字段
6. 围绕关键行为补充前后端测试

### 不纳入范围

1. 修改现有 `/chat`、`/stream`、`/report` 的外部接口协议
2. 全面重做 prompt 体系或工具定义方式
3. 新增 update / delete 一类 AI 写操作
4. 把 AI 模块重构成完整“平台中台”
5. 顺手扩展与本次目标无关的新功能

## 设计方案

## 1. 前端分层设计

### 1.1 目标

把当前巨型组件拆成“壳层 + 会话层 + 动作层”，降低单组件内的 watcher、副作用和状态耦合。

### 1.2 建议分层

#### 壳层

负责纯 UI 容器能力：

1. 弹窗开关
2. 拖拽与缩放
3. 桌面 / 移动端布局差异
4. 外层容器样式和滚动区域承载

壳层不再直接处理消息发送、流式状态和 action 生命周期。

#### 会话层

负责会话主线：

1. 用户输入与发送
2. assistant 占位消息创建
3. 历史消息持久化
4. 流式文本更新
5. 最终 markdown 定稿
6. 自动滚动与跟随策略
7. 图片输入、建议词、报告入口等会话相关能力

会话层只关心“消息”，不负责业务动作状态机。

#### 动作层

负责业务动作侧线：

1. `slot_request` 展示
2. `action_preview` 展示
3. `action_result` 展示
4. 候选项点击回填
5. 明确确认提交动作

动作层不再自行推断最后一条 assistant 消息的生命周期。

### 1.3 前端统一状态模型

建议引入统一的 AI 会话状态，而不是分散在多个 watcher 中拼接。

推荐状态拆分为三组：

#### 消息主线

1. `messages`
2. `pendingAssistantMessage`
3. `historyPersistenceState`

#### 动作侧线

1. `actionState = idle | collecting_slots | awaiting_confirmation | submitted | failed`
2. `actionCardPayload`
3. `actionError`

#### 流式过程

1. `requesting`
2. `streaming`
3. `tool_running`
4. `completed`
5. `failed`

关键原则：

1. 文本消息只表示文本消息。
2. 动作卡片只表示动作状态。
3. 流式过程只表示请求执行阶段。
4. 三者可以并行展示，但不互相覆盖。

### 1.4 对现有组件的优化方向

#### `AIChatWidget.vue`

从“全功能实现组件”收缩为“外层容器 + 组合子协调者”。

#### `useAIStream.js`

保留其对 SSE 事件的处理价值，但职责要进一步清晰：

1. 负责接收并归约后端 SSE 事件
2. 不负责最终消息持久化的全部细节
3. 对上层暴露更明确的事件/状态结果，而不是让组件再进行二次推断

#### `SlotQuestionCard.vue`

重点优化交互恢复能力：

1. 候选选择后高亮而非彻底锁死
2. 提供明确的“重新选择”路径
3. 当识别失败时，向用户说明可输入序号、名称或 ID
4. 多字段待补时，明确提示当前输入将补哪个字段

## 2. 后端分层设计

### 2.1 目标

把当前 `functions/lib/hono/routes/manage/ai.js` 拆成“薄路由 + 会话服务 + 动作服务 + 流引擎”的协作结构，在不改变对外协议的前提下，把重复逻辑和混杂职责分离出去。

### 2.2 路由层

路由层只负责：

1. 读取请求参数
2. 组装 `env`、`user`、`context`
3. 调用对应 service
4. 输出 JSON 或 SSE

路由层不再直接承载大段业务流程与通用逻辑。

### 2.3 会话服务

负责普通 AI 会话的公共前处理和后处理：

1. 构造 system prompt
2. 判断 `visionFirst`
3. 汇总输入模态信息
4. 统一 chat / stream 的消息预处理
5. 统一模型切换 telemetry
6. 统一注入信号检测入口

这样可以避免 chat 与 stream 在“同一类准备逻辑”上逐渐分叉。

### 2.4 动作服务

负责业务动作链路：

1. 从 context 推导可复用槽位
2. 识别显式确认语义
3. 创建并调用 orchestrator
4. 把 orchestrator 输出映射成 SSE 或 JSON 可消费结果

动作服务与普通问答分离，确保 AI 创建流程具备独立演进空间。

### 2.5 流引擎

负责流式协议执行层：

1. 解析模型 SSE chunk
2. 进行 content gate 过滤
3. 提取 tool calls
4. 控制工具调用轮次
5. 产出 `text_delta`、`tool_call`、`tool_result`、`done`、`error` 等标准 SSE 事件

当前 `processStreamToSSE()` 与 `handleToolCallsToSSE()` 应收敛进该层，避免继续作为路由文件内的“内部超大辅助函数”。

## 3. Action 生命周期设计

### 3.1 设计目标

把 AI 业务动作从“夹杂在文本中的特殊情况”，提升为明确的状态机流程。

### 3.2 状态机

推荐状态：

1. `idle`
2. `collecting`
3. `awaiting_confirmation`
4. `submitting`
5. `completed`
6. `failed`

说明：

1. `collecting` 表示仍有待补槽位。
2. `awaiting_confirmation` 表示已具备可提交数据，但必须等待用户显式确认。
3. `submitting` 用于承接提交中的瞬时状态。
4. `failed` 用于显式承接可恢复失败，而不是直接回到“什么都没发生”的状态。

### 3.3 Action 与消息的关系

1. assistant 文本回答不是 action 状态来源。
2. 前端应优先以结构化事件驱动 action 卡片，而不是解析自由文本。
3. action 事件可以与 assistant 文本并行出现，但二者不互相替代。

### 3.4 候选补槽策略

当前逻辑可继续沿用“候选项 + 文本补全”双通道，但应增强为：

1. 优先识别当前待补槽位
2. 当只有一个待选字段时，可继续支持序号 / 名称 / ID 匹配
3. 当有多个待选字段时，前端明确高亮当前待补字段，后端避免做过度隐式猜测
4. 候选项未命中时，返回更明确的可恢复提示，而不是简单重放原 prompt

## 4. 交互体验设计

### 4.1 补槽卡片

优化重点：

1. 明确展示“还缺哪些字段”
2. 区分“有候选可选”和“需要手动输入”的字段
3. 降低误选后的恢复成本
4. 让用户始终知道下一步该做什么

### 4.2 预览卡片

预览卡片应承担两个作用：

1. 作为最终提交前的结构化摘要
2. 作为失败恢复时的稳定回退点

当提交失败时，优先保留预览卡片而不是把用户打回空白对话状态。

### 4.3 提交结果卡片

提交结果卡片应明确展示：

1. 创建成功的实体标识
2. 推荐跳转或查看模块
3. 是否已触发静默刷新

即使刷新失败，也不应影响用户对“创建已成功”的认知。

## 5. 错误处理与恢复设计

### 5.1 前端统一错误分类

建议统一成以下类别：

1. `network_error`
2. `model_error`
3. `tool_error`
4. `action_error`
5. `input_error`

错误分类的目的不是增加抽象层，而是统一：

1. toast 文案策略
2. assistant 占位消息保留或清除策略
3. actionCard 是否保持当前状态
4. 用户下一步该如何恢复

### 5.2 Action 失败恢复

#### 补槽失败

保持在 `collecting`，并指出当前可输入的有效格式。

#### 确认提交失败

保持在 `awaiting_confirmation` 或 `failed`，并保留原预览内容，允许用户修正后重新提交。

#### 提交成功但刷新失败

仍展示成功结果，只单独提示模块可能未自动刷新。

### 5.3 Tool 调度失败

当工具调用轮次达到上限或执行失败时，应向前端发送明确反馈，而不是仅在服务端记录日志。用户侧需要看到可理解的结果，例如：

1. 当前请求过于复杂，建议缩小范围
2. 工具执行中断，请稍后重试或换一种表达

## 6. 可观测性设计

### 6.1 统一日志字段

建议围绕一次 AI 请求统一记录：

1. `requestId`
2. `userId`
3. `sessionId`
4. `routeType`
5. `visionFirst`
6. `selectedModel`
7. `modelSwitched`
8. `toolRounds`
9. `executedTools`
10. `actionKind`
11. `entityType`
12. `finalStatus`

### 6.2 关键日志节点

只保留关键阶段日志，避免无效噪音：

1. 请求进入
2. action 命中 / 未命中
3. 模型切换
4. tool round 结果
5. 候选命中 / 未命中
6. action submit 成功 / 失败
7. stream 完成 / 中断

这样既能保证排障效率，也不至于让 AI 路径的日志量失控。

## 7. 测试策略

### 7.1 前端测试

重点覆盖：

1. SSE 事件归约到前端状态的过程
2. assistant 占位消息与最终定稿逻辑
3. actionCard 状态切换与渲染
4. 补槽候选点击、重选与确认交互
5. 异常路径下的 UI 恢复行为

### 7.2 后端测试

重点覆盖：

1. chat / stream 共用前处理逻辑
2. action service 的上下文补槽与确认识别
3. stream engine 的 tool round 上限与失败事件
4. 多候选字段与未命中场景
5. action 成功后的 refresh 事件输出

### 7.3 测试原则

测试以“关键行为边界”为中心，而不是仅验证表层渲染：

1. 状态是否正确流转
2. 失败是否可恢复
3. 文本流与动作流是否互不污染
4. chat / stream 是否保持一致语义

## 8. 分阶段落地建议

### 第一阶段：前端状态收敛

1. 拆分 `AIChatWidget` 责任边界
2. 统一消息流 / 动作流 / 流式过程状态
3. 优先解决用户可见的错位与交互僵硬问题

### 第二阶段：后端结构拆分

1. 提取 conversation service
2. 提取 action service
3. 提取 stream engine
4. 让 `ai.js` 回归薄路由

### 第三阶段：体验与测试补强

1. 补槽恢复能力细化
2. 错误反馈统一
3. 行为测试补齐
4. 遥测字段收口

这个顺序的目的，是先稳定用户直接感知到的问题，再整理后端结构，最后补充回归保障。

## 验收标准

1. `src/components/common/AIChatWidget.vue` 不再同时承担窗口层、会话层和动作层全部职责。
2. 前端消息状态、action 状态与流式过程状态具备清晰边界，不再依赖多处 watcher 互相修补。
3. `functions/lib/hono/routes/manage/ai.js` 明显瘦身，chat / stream 的公共准备逻辑被提取复用。
4. 补槽、预览、确认、提交流程在失败情况下具备明确可恢复路径。
5. tool 调度异常、图片输入异常、流式中断等关键失败场景在用户侧有明确反馈。
6. 关键日志字段统一，能够定位一次请求的模型、工具、动作与最终状态。
7. 前后端新增测试能够覆盖本次优化涉及的关键行为边界。

## 结论

本次 AI 模块整体优化不追求“大而全”的重构，而是以“分层收敛、状态清晰、交互可恢复、行为可验证”为核心目标，在保留现有能力与协议的前提下，为后续继续扩展 AI Action、Tool Calling 和多轮业务交互建立更稳固的基础。
